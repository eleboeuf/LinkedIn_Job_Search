CANONICAL RULE — GMAIL LABEL SEARCH: DISPLAY NAME, NEVER INTERNAL ID. (Consolidated here on
7 July 2026 — this exact rule used to be repeated near-verbatim in both
skills/check-job-status/SKILL.md and skills/read-all-alert-emails/SKILL.md; both files now
point back here instead of restating it.) Every Gmail search in this project — whether
against gmail_job_alerts_label or gmail_job_applications_label — must use the label's
human-readable DISPLAY NAME (e.g. `label:Linkedin-Alerts`, `label:Jobs`), never its internal
ID (e.g. `label:Label_229824024361616313`). The `list_labels` tool returns both a `name`
(display name) and an `id` (internal ID) — always use `name`. Using the internal ID does not
raise an error, it silently returns zero results, which is what makes this mistake dangerous:
a whole day's label-filtered search can come back empty with no visible failure. Replace
spaces in the display name with hyphens in the query string (e.g. "Linkedin Alerts" →
`Linkedin-Alerts`).

CANONICAL RULE — UNIQUE ROLE IDENTIFIER: COMPANY + TITLE + LOCATION (added 8 July 2026,
per user request). Everywhere else in this document that says "company+title" or "same
company + same job title" as the key for deciding whether two job postings are the SAME
role (repost/scoring dedup, report-level rendering dedup, section-exclusivity checks,
reconciliation duplicate checks) — that key is COMPANY + TITLE + LOCATION, all three
normalised, not company+title alone. Concretely:
- Normalise company (strip trailing parenthetical annotation, lowercase, strip
  punctuation/whitespace — as already specified under the MATCHING KEY BUG section below),
  normalise title (lowercase, strip punctuation/whitespace), and normalise location the
  same way (lowercase, strip punctuation/whitespace; treat obvious equivalents as the same
  location, e.g. "London" = "London, UK" = "Greater London" = "London Area, United
  Kingdom" — but do NOT treat genuinely different cities/areas as equivalent).
- Two postings are the SAME role only if company, title, AND location all match after
  normalisation. Example: the same company posting the same job title once for London and
  once for Manchester is TWO separate roles — score each independently, and both may appear
  in the report as distinct entries. If the location is the same (or normalises to the
  same place), it is ONE role, and the existing repost/dedup/exclusivity rules apply as
  before (merge-then-score, one card/row, one section only, etc.).
- This is the ONE normalisation function used everywhere in this project that needs a
  same-role check — do not maintain a second, slightly different company+title-only
  normaliser anywhere (scoring dedup, report dedup, feedback matching, reconciliation).
Wherever this document below still literally reads "company+title" in an explanatory
sentence, read it as shorthand for this company+title+location key.

          data and first_seen set to today's date (the job ID is genuinely new so it's a new
          first_seen, but the SCORE is reused, not recomputed).
        - If no match is found → it is genuinely new (including a same company+title role in
          a new location); proceed to step 3 and score it normally.
      This rule governs SCORING only. cache/jobs_page_cache.json entries are never merged
      across job IDs — each posting keeps its own open/closed/salary/applicant data, since a
      repost can have a different open/closed status than the original (e.g. the original
      listing closes while the repost stays open, or vice versa).
   After processing all jobs, save cache/jobs_seen_cache.json with last_updated set to now
   (per the INCREMENTAL CACHE WRITES rule above, write after each batch rather than only once
   at the very end of the run).

   If use_cv_for_scoring is false → use the rubric only; do NOT reference the CV.

   STRUCTURE of cache/applications_cache.json (a "location" field was added 8 July 2026 —
   see the CANONICAL RULE — UNIQUE ROLE IDENTIFIER section above; populate it when the
   application/rejection email or the matching job posting states a location, leave it null
   if genuinely unknown — do NOT backfill or guess it for pre-existing entries that predate

   {
     "last_processed_at": "<ISO 8601 UTC timestamp>",

         "title": "Head of Partnerships",
         "location": "London or null",

             "application_email_id": "<Gmail message id or null>",
             "rejection_email_id": "<Gmail message id or null>"
           }
         ]
       }
     ]
   }
   Multiple applications to the same role are stored as multiple objects in "events".

   STEP 7a — UPDATE THE CACHE before generating the report:
   a. If cache/applications_cache.json does not exist (first run / bootstrap):
      - Scan ALL emails in gmail_job_applications_label received in the past
        application_lookback_days days (from config.json).
      - Build cache/applications_cache.json from scratch using the matching rules below.
      - Set last_processed_at to the current UTC timestamp and save the file.
   b. If cache/applications_cache.json exists:
      - Read last_processed_at from the file.
      - Scan ONLY emails in gmail_job_applications_label received AFTER last_processed_at
        (delta scan — typically 0 to a handful of emails).
      - Process each new email using the matching rules below.
      - Update last_processed_at to the current UTC timestamp and save the file.

   MATCHING RULES — normalise company name, job title, AND location before matching
   (lowercase, strip punctuation, trim whitespace — per the CANONICAL RULE — UNIQUE ROLE
   IDENTIFIER section above). Location comes from the application/rejection email body or
   the matching job posting when stated; if the email doesn't state a location, or the
   existing entry predates the "location" field and has it null, fall back to matching on
   company+title alone rather than treating the match as failed — location disambiguates
   when available, it does not replace company+title matching when it isn't:
   - Application confirmation email:
       • Find existing entry (company + title + location, or company + title if location
         is unavailable on either side) where the most recent event has rejected_date: null
         (a pending application).
       • If found → this is a re-application: append a NEW event to the events array
         (applied_date set, rejected_date: null). Store Gmail id in application_email_id.
       • If not found → create a new entry (with location if known, else null) with one
         event (applied_date set, rejected_date: null). Store Gmail id in
         application_email_id.
   - Rejection email:
       • Find existing entry (company + title + location, or company + title if location
         is unavailable) where the most recent event has rejected_date: null.
       • If found → set rejected_date on that event. Store Gmail id in rejection_email_id.
       • If not found in cache/applications_cache.json (application was missed, OR the entry has
         already been archived — see STEP 7c) → FALLBACK: search cache/applications_archive.json
         for an entry (company + title + location, or company + title if location is
         unavailable) whose most recent event has rejected_date: null.
           - If found in the archive → move that entry BACK into cache/applications_cache.json,
             set rejected_date on its most recent event, and store the Gmail id in
             rejection_email_id. Decrement archived_count and archived_pending in
             cache/applications_archive.json (the entry now lives in the live cache, so it is
             counted there instead of in the archive).
           - If not found anywhere (no cache match, no archive match) → create a new entry
             in cache/applications_cache.json with one event (applied_date: null, rejected_date
             set). Store Gmail id in rejection_email_id.
       This fallback only runs when the live-cache lookup misses — it is not a per-run scan
       of the archive, only an occasional check on unmatched rejection emails.
   - Skip any email whose Gmail message id already exists in the cache OR the archive
     (already processed).

   STEP 7c — ARCHIVE STALE ENTRIES (runs once per calendar month, not on every run):
   Check last_archived_at in cache/applications_archive.json (if the file doesn't exist yet,
   treat last_archived_at as absent and proceed). If last_archived_at falls in the SAME
   calendar month and year as today → skip this step entirely (already run this month).
   Otherwise (different month/year, or archive file doesn't exist yet) → run the archiving
   pass below, then set last_archived_at to now.
   This intentionally does not require the run to fall exactly on the 1st — it triggers on
   the first run of a new calendar month, so a skipped day on the 1st doesn't delay
   archiving until the following month.

   For each entry in cache/applications_cache.json, find its most recent event (by applied_date,
   or rejected_date if applied_date is missing). If that date is older than
   applications_archive_after_months months ago (from config.json) — regardless of whether
   the entry is rejected or still pending with no response — move the entry from
   cache/applications_cache.json to cache/applications_archive.json.
   cache/applications_archive.json structure:
   {
     "archived_count": <int>,
     "archived_rejected": <int>,   // archived entries whose most recent event is rejected
     "archived_pending": <int>,    // archived entries whose most recent event is still pending
     "last_archived_at": "<ISO 8601 UTC timestamp>",
     "applications": [ ...entries... ]
   }
   If cache/applications_archive.json does not exist, create it with zeroed counters and an empty
   applications array before archiving. Update archived_count / archived_rejected /
   archived_pending to stay in sync with the applications array whenever entries are added
   to or removed from the archive (including the fallback move-back in the MATCHING RULES
   above). cache/applications_cache.json's last_processed_at is unaffected by archiving.

   STEP 7d — USE THE CACHE IN THE REPORT:
   For each job in today's report, look up company + title + location (falling back to
   company + title if either side lacks a location) in cache/applications_cache.json only
   (archived entries are historical and won't correspond to jobs in a current report).
   Status is determined by the MOST RECENT event in the events array:
   - applied_date set, rejected_date null → 🟠 Applied <date>
   - rejected_date set → 🔴 Rejected <date>
   - No match → no status badge.

   MATCHING KEY BUG (fix required) — a job was once missed (Grey Matter Recruitment,
   "Partnership Director, Europe") because the report displayed an enriched company name
   with a parenthetical annotation appended for readability (e.g. "Grey Matter Recruitment
   (AI-Native MarTech client)"), and that SAME enriched string was then used as the lookup
   key against applications_cache.json — which only stores the bare company name ("Grey
   Matter Recruitment"). The match silently failed and the status badge was dropped.
   To prevent recurrence: always normalise the company name for matching by stripping any
   trailing parenthetical annotation — e.g. strip " (...)" — plus the standard lowercase/
   punctuation/whitespace normalisation from the check-job-status skill, BEFORE doing the
   cache lookup. The parenthetical annotation may still be shown in the card/table for
   readability, but it must never be part of the matching key. The same normalisation
   (lowercase/strip punctuation/whitespace, treating obvious equivalents like "London" and
   "Greater London" as the same place) applies to the location component of the
   company+title+location key introduced 8 July 2026 (see the CANONICAL RULE — UNIQUE ROLE
   IDENTIFIER section above) — an enriched or differently-formatted location string must
   never cause a false mismatch either.

    search URL filtered to 1st-degree connections at that company:
      https://www.linkedin.com/search/results/people/?currentCompany=%5B%22COMPANY_ID%22%5D&network=%5B%22F%22%5D
    MANDATORY (for status_override "follow-up" entries only) — L1_contacts_url must be
    populated automatically whenever:
    - A new "follow-up" entry is created in inputs/job_feedback.json, OR
    - An existing entry's status_override is changed to "follow-up", OR
    - The company name of an existing "follow-up" entry is changed.
    Process to build L1_contacts_url:
    1. Navigate to https://www.linkedin.com/search/results/companies/?keywords=COMPANY_NAME
       via Chrome browser tools.
    2. Identify the correct company in the results (match name and industry context).
    3. Navigate to that company's LinkedIn page.
    4. Extract the numeric company ID from the page DOM:
         document.body.innerHTML.match(/urn:li:fsd_company:(\d+)/)
       The FIRST match is the company's own ID.
    5. Set L1_contacts_url to:
         https://www.linkedin.com/search/results/people/?currentCompany=%5B%22ID%22%5D&network=%5B%22F%22%5D
    6. Navigate to that search URL and read the page text to extract 1st-degree contacts:
       - Count how many "• 1st" results appear.
       - If 0 contacts → set L1_contacts_url to "" and L1_contacts to [].
       - If 1–3 contacts → extract each person's name and profile URL
         (use document.querySelectorAll('a[href*="/in/"]') and match against names
         in the page text). Store as L1_contacts: [{name, url}, ...].
       - If 4+ contacts → leave L1_contacts as [] (display handled via L1_contacts_url).
    7. If the company cannot be found on LinkedIn, or the page is unavailable,
       set L1_contacts_url to "" and L1_contacts to []. Do NOT leave either unset.
